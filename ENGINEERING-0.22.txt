GTA V iOS NATIVE 0.22 — STAGE 3 ENGINEERING REPORT
2026-10-14 (America/Sao_Paulo). Stage 3 remains active; five stages left.

RESULT
Unsigned ARM64 Native 0.22.0/build 22 passed the independently available CI
and package checks below. A valid original 2D SRV is no longer forced into a
cube view when a proven uniform branch makes its cube sample unreachable.
Active cube paths, unknown control flow and invalid descriptors still fail
instead of receiving fabricated faces, dummy visibility or skipped draws.

The supplied descriptor establishes the immediate interface mismatch. The
phone's original CREATE_TEXTURE/UPLOAD_TEXTURE history and light-type uniform
were not supplied. We cannot infer those missing historical values or claim
the physical crash is resolved before that conditional path is exercised on
the phone. Sustained correct scene animation and gameplay are not verified.

1. EXACT FAILURE AND RESOURCE TRACE
Source 708: DXGI 71 / native 50 (BC1 RGBA UNORM), 4 x 4 x 1, one mip,
version 2. SRV 709: [709,0,708,71,4,0,1,0,0]. The original D3D SRV dimension
4 is TEXTURE2D. Shader binding 46 maps to pixel texture slot 14; its WGSL
declaration is texture_depth_cube. The old consumer selected the shader's
cube dimension and requested six layers from the one-layer source. It also
attempted a color-to-depth proxy for this compressed color source.
This is not a remaining-mip or UINT_MAX array-range case.

The exact unchanged shaders are:
  VS a276344f1111242f: ped_alpha / VS_PedTransformSkin
  PS 996bb42f448956f2: ped_alpha / PS_PedTextured_Four
The PS contains separate cube and spot shadow resources in one static shader.
For light zero, cb6[15].w == 0 disables the shadow sample; == 3 selects the
2D spot resource; other values select the cube path. Other light selectors
are at cb6[19].w, [23].w and [27].w. The same source supplies the proof;
these branches were not guessed from a resource's size or its pixel color.

Approved original-engine disassembly was inspected without modifying it:
  function 326 copies D3D11_TEXTURE2D_DESC into the resource;
  function 268 forwards width/height, mip count, max(1, ArraySize), format,
  bind flags and sample count, then uploads mipCount * arrayCount records;
  function 328 serializes the SRV dimension and range. Cube counts already
  become faces at the producer; the consumer must not multiply again;
  native create_texture takes packet field 6 as the 2D array-layer count;
  uploads use the serialized layer and mip. Version starts at 1 and changes
  after writes; resource-ID destruction changes the binding-cache epoch.
No six-to-one reduction was found in these producer/consumer code paths.
That does not reconstruct the missing physical creation packet. Version 2
alone does not establish which write produced the phone's current contents.

New bounded per-resource history retains the original ten-word creation
packet, last twelve-word upload header, upload count/command, first up-to-eight
upload bytes, version and latest stage/slot binding command. Failing range
reports retain all nine SRV words, formats, dimensions and shader expectation.
The inactive/active decision also reports the actual uniform words/values.
This is live history from the next run, not invented past device events.

2. CORRECT COMPATIBILITY FIX
shadow_guard_reflect.inc recognizes only a narrow, structured translator
pattern: an immediate uniform f32 equality test, select/bitcast boolean and
its corresponding lexical true arm. The uniform must be an element of
the original sole packed vec4<f32> array. Only a depth-cube resource with one
direct comparison-sample use can be certified. Extra uses, aliases, comments,
unknown forms, storage writes or unproven conditions preserve normal binding
validation. There are at most eight proof entries and 32 control regions.

Before each DRAW, the GPU service reads the exact same constant-buffer shadow,
first-constant offset and zero-filled missing-byte convention as draw_group.
For a valid original one-layer 2D SRV with a compatible format, it can remove
the cube declaration and its sample expression only if an enclosing guard is
false for that draw. The replacement expression is unreachable; it never
substitutes zero for an executed texture sample. All other shader operations,
uniform tests, clipping, interpolation and outputs are retained.

The original texture, 2D SRV, compressed bytes and layer count are unchanged.
Proofs use raw f32 bits for exact signed-zero/three equality. Subnormals,
NaN and infinity never certify removal; packed-uniform shadowing and else-arm
inference are rejected. Uniform or resource changes are re-evaluated for every draw. Active cube
mismatches still produce the full error, now before an unnecessary pipeline
creation. Valid six-face cubes continue to use actual face/mip data.

Before retiring a shadow or storage variant, pending commands are submitted
so Destroy cannot invalidate resources still referenced by an unsubmitted
encoder. This uses the existing submission/uniform-ring rules, without a new
per-draw GPU completion wait.

Variants are bounded to four per live source shader with eviction/recreation
and shared-constant reference ownership. The pipeline key includes the
inactive-binding mask. Existing storage variants, 128-entry scene pipeline
cache, resource lifetime rules, queries and compute behavior remain intact.

4. PERFORMANCE ROOT CAUSE AND MEASUREMENTS
Confirmed cache defect: DrawKey copied the input-layout object's ID along
with its descriptor. Two independently owned identical layouts therefore
produced different keys and redundant pipeline API calls. Only the ownership
ID is now removed from the key; all semantic descriptor words remain.
Ownership, destruction and resource-binding invalidation are unchanged.
The old behavior is retained only behind a CLI regression-test flag.

Reproducible fixture results (same geometry/pixels):
  Two equivalent layout IDs alone: pipeline creations 2 -> 1.
  Complete six-draw fixture, including a truly changed descriptor:
    old key 3 creates / 3 hits; semantic key 2 creates / 4 hits.
  Run/mode 1: semantic key, total pipeline API CPU wall 13.951 ms.
  Run/mode 2: 0.21 reference, total pipeline API CPU wall 1.591 ms.
  Run/mode 3: semantic key, total pipeline API CPU wall 0.942 ms.
  Run/mode 4: 0.21 reference, total pipeline API CPU wall 1.508 ms.
Driver cache warmth and execution order affect these CPU times. The verified
improvement is avoiding a redundant API call, not an iPhone FPS percentage.
  Retained nine-read fixture 1: submit/map CPU mean 8.534 ms, max 24.463 ms.
  Retained nine-read fixture 2: submit/map CPU mean 13.215 ms, max 40.232 ms.
  Exact reported ped_alpha pair, first-use API CPU wall on CI:
    modules 6.311 ms; inter-stage link 0.792 ms;
    pipeline creation 334.241 ms.
The exact-pair result independently confirms that pipeline creation can be
expensive in this backend. It does not identify the cause of the phone's
particular 411.418 ms call or prove that cache identity caused that miss.
No physical-device before/after benchmark or true GPU execution timing is
available for 0.22. No 30-FPS result or guarantee is claimed.

The latest supplied phone data remains: 96.066 ms mean post-compute PRESENT
interval over 17 samples; max pipeline API 411.418 ms; max upload handler
68.852 ms; max actual display interval 616.723 ms; earlier observed scene
approximately 5-8 FPS. These maxima are not time-correlated samples and may
overlap. They cannot be summed, subtracted from the mean, or interpreted as
a sustained gameplay frame-rate measurement. Quantiles need more samples.

5. NEW BOTTLENECK DIAGNOSTICS
The GPU service retains eight worst CPU PRESENT intervals and eight slow
commands >=8 ms. Each frame record has a sequence/timestamp, command/draw and
pipeline create/hit/evict counts, upload bytes, handler/upload/allocation
wall time, module/link/pipeline/shadow work, readback/completion waits,
producer-idle time and drain-flush time. Slow uploads report the preceding
mutation flush separately, because that flush is part of handler duration.
The 68.852 ms upload maximum therefore was not necessarily transfer time.
Records are emitted once on cleanup; storage and hot-path work remain bounded.
Nested categories overlap and must not be added. These are CPU submission
records, not displayed frames, isolated engine CPU or GPU execution times.

The prior callback post-completion sleep fix, actual drawable timestamps,
historical-FPS age indicator and bounded average/median/p95/p99/worst windows
are preserved. Loading screens and first-compute markers do not identify
gameplay. The old 2.777-second exposure wait is not yet established as fixed
or recurring: earlier compilation/ring work and uniform-ring completion can
contribute. Real bytes are still copied before release-ordered publication;
no stale data or premature completion was introduced. Mapping and queue
ordering were not rewritten speculatively.
