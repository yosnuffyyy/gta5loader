CONFIRMED ROOT CAUSE
Native0.30 resets the engine deadline to180 seconds in native_boot_prepare_options.
native_wait_cancelled then checks that deadline throughout the whole session;
there was no startup-to-live transition. Reaching the vault did not retire it.
The supplied fatal report is a watchdog termination, not evidence of a vault
shader, SRV, asset or mission crash. Working touch input/vault progress is user
reported physical evidence; the new build is not yet physically verified.

RUNTIME FIX
The real display-enabled, non-checkpoint Prologue uses a separate session policy.
Startup keeps its180-active-second deadline. A real animated-camera engine log,
a subsequent original simulation pad hook and a subsequent successful PRESENT
must all occur before entering LIVE. Old loading frames and draw counts alone
cannot qualify. This establishes liveness, not correct scene pixels or gameplay.
LIVE has no total-duration cutoff. It stops after60 active seconds without an
engine pad-update hook or delivered asset data, or without a successful PRESENT
or delivered asset data. Positive bytes stored in engine memory extend genuine
loading progress; failed, empty and EOF-only requests cannot manufacture it.
Long cutscenes and in-game pause remain valid while hooks/presentation advance.
Settings and app interruptions suspend the active clock. Backgrounding safely
stops the session as before; returning does not resume a background engine.
User cancellation wins even if a policy poll was waiting on its lock. First
fatal reason is retained. Diagnostic/checkpoint deadlines and15-second GPU
callback protection remain. The monitor reuses existing wait/status paths,
amortizes checks to at most10Hz and creates no new polling thread or GPU wait.
Bounded reports show phase, active time, engine/frame/IO ages, last script,
GPU phase/opcode/shader and worker/proxy/mailbox state. Existing engine freeze
profiling and display-timestamp diagnostics remain.

VERIFIED INPUT QUEUE FIX
A leading obsolete analog-only state could delay a later fire/release edge by
one engine hook after a render stall. The consumer now skips only leading states
whose buttons exactly match the last state actually delivered, and only when a
newer queued state exists. Every button edge, tap, source-handoff neutral and
focus release remains ordered. The controlled1.8-second-stall test delivers
movement+fire or release on the next hook; the previous algorithm required two
hooks by source analysis. This does not deliver input while the simulation is
blocked on rendering and does not establish improved physical-device latency.
No UI-thread engine-memory writes, controller polling or new GPU waits.
The latency label now explicitly means oldest coalesced event to engine hook;
the original coalescing preserved the oldest timestamp, not the latest gesture.

VERIFIED GPU STAGING ACCOUNTING FIX
Successful ordered readback mapping already retires prior queue submissions,
but0.30 kept their uniform batches counted as pending until an explicit wait.
The same retirement helper now clears only submitted accounting after a valid
mapped readback. Unsubmitted draw constants remain intact. Failed mappings do
not retire accounting. Caps remain16 batches/4MiB and1MiB readback staging.
The actual Metal fixture compares corrected and0.30-reference accounting:
96 changing draws,13 exact readbacks,256 checked pixels and96 exact occlusion
samples per mode, in each of two independent runtime processes.
Pressure waits:6 ->0. Explicit completions:7 ->1. Draws/readbacks/pixels unchanged.
This is a fixture operation-count reduction, not a measured iPhone FPS gain.
Exact measured CPU wait times are retained in benchmark-comparison.json;
driver timings vary and are not a sustained-gameplay benchmark.
Queue-order evidence was checked against pinned wgpu-core29.0.3 map_async and
submission retirement implementation, not assumed from a successful build.
