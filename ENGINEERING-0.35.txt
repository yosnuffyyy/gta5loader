CONFIRMED ALLOCATOR DEFECTS
The pinned v7 reduced-memory profile caps each GrowBuddy segment at 32 MiB.
An 8 KiB sentinel prevents a full-segment buddy block; its largest initial block
is 16 MiB. A 37,314,560-byte resource demand rounds to a 64 MiB buddy block,
which the selected power-of-two growth policy satisfies with a 128 MiB segment.
Even an empty 32 or 64 MiB segment cannot satisfy it. An isolated 64 MiB + 8 KiB
segment can satisfy it, but the mixed-allocation experiment retained 134,217,728
bytes in two segments versus 134,209,536 bytes in one 128 MiB segment. That
minimum-only policy consumed an extra fixed slot without saving retained memory,
so it was rejected. This is not a claim that 128 MiB is an absolute minimum.
The exact fatal string originates in original pgRscBuilder::AllocateMap (f2040),
which delegates to the resource-class allocator (class 1). The native constructor/root-allocation probe
identifies a 1 GiB growth target for the actual class-1 allocator. This target is NOT a global
maximum heap budget. The independent fixed limit is 32 segment slots; the native
linear-memory address space is still capped at 4 GiB.

The v7 GetMemoryAvailable implementation replaced original actual free accounting
with growth-target minus live usage. The original profile explicitly requires
growable headroom for streamer preflight, rather than currently committed free.
However, this can underflow unsigned arithmetic and ignores exhausted segment
slots. Restoring actual-free-only accounting would regress that preflight.
A retained original 279-byte reference function establishes the original contract.
Original-Wasm experiments reproduce the failure, fixed-slot exhaustion, and the
bad available value. No original asset or production Wasm byte was modified.

NATIVE FIX
A checked generated-C adaptation retains the original allocation/free/locking
algorithms. Request-aware growth selects 32/64/128/256 MiB segment granularity,
within the original 256 MiB per-segment cap. Slot reserve increases granularity
as the fixed 32-slot arena fills, including proactive growth paths. It does not
increase the linear address limit or promise an OS memory budget. Larger chunks
can retain more virtual/committed memory; device pressure still matters.
The profile preflight contract is preserved as actual retained free plus logical
growth headroom, bounded by remaining slots and the original segment cap. Full
arenas report actual retained free; live usage above target cannot underflow.
Potential growth is also bounded by the absolute 4 GiB linear address limit.
The getter does not proactively allocate or promise OS memory.

Native archive service rejects nonempty NULL destinations before file I/O or
memory writes. Zero-length requests remain valid. A bounded last-eight request
history and allocator retry/failure snapshots retain owner/request/actual free/
largest block/segment/linear committed data for the next transition. There is
no invented buffer, fabricated successful asset read, or whole-archive cache.
The one 64 KiB reader buffer/eight descriptors remain unchanged.

SUBMISSION / UNIFORM WORK
Every native GPU-buffer upload previously flushed pending draws, even if those
commands did not reference that buffer. Per-object encoder epochs now record
vertex/index/indirect/storage buffer reads and writes, plus non-draw UAV clears
and counter-copy destinations. Only independent uploads avoid a submission. Existing render-pass usage/barrier
scopes are preserved rather than accidentally merging storage/vertex hazards.
Overlapping or unknown hazards retain conservative flushes. Cached binding groups
still mark the current source owner; resource replacement gets a fresh epoch.
An explicit 64-bit wrap guard remains conservative. No new staging allocation,
GPU wait, relaxed ordering, or uniform-data approximation is introduced.
The service also previously submitted after every 256-command ring drain,
even when already-published commands remained ready. A separate bounded policy
retains an encoder only across full drains with ready work, up to four drains
or a 4 ms clock check. It never waits for more producer work, never sleeps with
an encoder pending, still polls callbacks/checks cancellation each drain, and
retains every original pass/query boundary. A long individual driver call is
not bounded by that 4 ms check. Explicit dependency/fence/readback/PRESENT
rules remain. Controlled-clock tests cover bounds and producer idle. Separate
GPU replay modes isolate legacy uploads, dependency-only, and coalescing; the
candidate must reduce submissions against dependency-only, with identical
pixels/query counts and final buffer bytes, or it is rejected.
Longer safe batches can reuse existing exact immutable uniform slices. The
256-entry pipeline cache, bounded staging, 640x360 baseline and 30 FPS cap remain.

PERFORMANCE PRIORITIES (EVIDENCE RANKING, NOT EXCLUSIVE CPU/GPU PERCENTAGES)
1. Submission fragmentation: reported 3.35 million submissions / 2.81 million
   draw batches / 9.51 million draws. The new fixture isolates unnecessary
   upload-triggered submissions; actual gameplay dependency frequency is unknown.
2. Upload/uniform traffic: 15 million protocol uploads and about 25 GB cumulative
   uniform traffic. Counts alone do not prove GPU memory-bandwidth saturation.
3. Staging and synchronization: 123,319 pressure waits; fewer unnecessarily split
   batches should reduce related pressure, but aggregate iPhone benefit is unmeasured.
4. Cold/recreated pipelines: 1,132 creates / 876 evictions in a 256-entry cache;
   worst creation approximately 593 ms. Latest aggregate evidence cannot identify
   exact redundant variants or establish a safe mission prewarm sequence.
5. Render-service backpressure / engine and input scheduling: prior frame profiles
   show simulation waiting for rendering. No exclusive latest simulation CPU or
   actual GPU timestamp measurements are available to assign a precise share.

BACKEND / PLATFORM AUDIT
Pinned Metal HAL pipeline-cache creation is a placeholder; a generic cache object
would not provide persistent Metal binary archives. No unsupported archive API
or unbounded pipeline retention was added. Actual game render targets are sampled,
copied or loaded later; no memoryless/aliasing/store elimination was applied
without proof of lifetimes. Existing compressed textures, depth proxies, clip
linking, queries, compute, readbacks and optional shadow compatibility are retained.
Thermal state is sampled in the existing five-second report; no clock override,
quality reduction, thermal workaround, independent polling timer or GPU wait.
No changes to audio, controls, shadow shader semantics or native UI navigation.
Standalone probe and shader-audit exits now close the host before releasing its
memory, including the new diagnostics mutex and existing asset/input services.

LIMITS / NEXT VALIDATION
The CI Metal adapter reports Apple Paravirtual device. Host replay is not a
physical A18 Pro scene test. No new iPhone FPS, real
GPU execution time, thermal sustainability, input latency or process-footprint
improvement is claimed. Post-funeral streaming, later mission resources and the
4 GiB address ceiling still require device evidence. 30 FPS needs 33.3 ms/frame;
the reported 7–9 FPS gameplay does not establish that. 16.67 ms processing
headroom remains research only; compilation, submission, synchronization, engine
work and unknown sustained GPU costs all remain obstacles.

VALIDATION HISTORY
The first combined candidate was rejected by the historical staging fixture:
it assumed an unused buffer forced a GPU submission. Candidate pixels and query
samples were correct, but that count assertion was no longer a real dependency.
The fixture now updates the buffer the shader actually consumes. This retains
its original assertions rather than weakening data/order tests. The same review
also retained the streamer's intentionally growable preflight contract instead
of restoring an actual-free-only getter. Only the final successful source/CI
identified in VERIFICATION-0.35.txt is deliverable.

A later candidate run stopped before tests because Windows line endings entered
the POSIX CI entry script. LF bytes were restored and the local source-preparation
step now rejects CR bytes in shell scripts. No failed build was released.
